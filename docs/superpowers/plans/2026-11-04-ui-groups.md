# UI Groups Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** A "UI group" where every mod has its own on/off switch, several can be on at once, toggled in game with no F10 reload, plus an import for loose mods.

**Architecture:** A UI group is a normal `group_G` folder with a marker file. Inside it, each mod is rewritten by the *existing* `_manageMod`, but as if it were alone in its own two-state group `group_K` (K = a free number in 1..500, stored in the mod folder). Slot 0 = off, slot 1 = on. Toggle = `simulateKeySelectMod(K, 0|1)`. The rewriter is untouched.

**Tech Stack:** Flutter/Dart, Riverpod, `package:path`, `flutter test`.

**Spec:** `docs/superpowers/specs/2026-11-04-ui-groups-design.md`

## Global Constraints

- Personal Dart code goes in new files under `lib/custom/`; edits to upstream files stay a few lines each (the self-update job merges upstream daily).
- Group numbers are 1..500 (`getGroupFolders` regex, cursor-Y key press). K must come from this range and must not equal any real `group_N` folder number.
- Marker files live inside the folder they describe, like `loadmode` and `equippedmod` (see `lib/custom/only_equipped_files.dart`).
- Windows PowerShell 5.1 only for scripts; Dart code must also compile for Linux (no Windows-only APIs outside existing patterns).
- Never edit `main`. Work on a feature branch off `my-version`.

## Review Focus

- Pool exhaustion: more UI mods than free numbers. Expect a clear log line, remaining mods skipped, no crash.
- Two mod folders with the same `uikey` (a folder was copied). Expect the second gets a new number.
- Garbage in `uikey` / `uistate`. Expect it treated as missing / off.
- Import when a folder with the same name exists in the target. Expect a safe unique name, nothing overwritten.
- A UI group set back to normal. Expect `loadmode` back to inherit and stale `group_K.ini` files removed on next Update Mod Data.

### Task 1: Pure file logic (`ui_group_files.dart`)

**Files:**
- Create: `lib/custom/ui_group_files.dart` (no Flutter imports, like `only_equipped_files.dart`)
- Test: `test/custom/ui_group_files_test.dart`

**Interfaces:**
- Produces:
  - `Future<bool> isUiGroupFolder(String groupPath)` — true if file `uigroup` exists in it.
  - `Future<void> setUiGroupFolder(String groupPath, bool on)` — creates/deletes `uigroup`.
  - `Future<int?> readUiKey(String modPath)` / `Future<void> writeUiKey(String modPath, int k)` — file `uikey`; non-integer or outside 1..500 reads as null.
  - `Future<bool> readUiOn(String modPath)` / `Future<void> writeUiOn(String modPath, bool on)` — file `uistate` ("1"/"0"); anything else reads false.
  - `Future<Map<String, int>> allocateUiKeys(List<String> uiModPaths, Set<int> usedRealGroupIndexes)` — returns modPath → K for every mod it could give a number. Keeps a mod's existing valid key if unique and not in `usedRealGroupIndexes`; otherwise assigns the lowest free number in 1..500 (free = not a real group, not a kept key, not already assigned) and writes `uikey`. Mods left without a number (pool empty) are absent from the map.
  - `String renderUiGroupIni(String template, int k)` — replaces `{x}` with `k` and `{group_x}` with `group_$k` in the contents of `assets/template_txt/template_group.txt`.

### Task 2: Make Update Mod Data rewrite UI groups

**Files:**
- Create: `lib/custom/ui_group_manage.dart`
- Modify: `lib/utils/mod_manager.dart` inside `updateModData`, in the `Future.wait([for (final entry in groupAndModsPair.entries) ...` block (~line 1420-1462).

**Interfaces:**
- Consumes: everything from Task 1; `ModData`, `_manageMod` (private, so it is passed in as a closure).
- Produces: `Future<Map<String, int>> prepareUiKeys(Map<(String, int), List<ModData>> groupAndModsPair)` — for every UI group, allocates keys for its non-disabled mods (skip index 0 "None" and mods whose folder name starts with `disabled`, case-insensitive), using all group indexes in the map as `usedRealGroupIndexes`. Returns modPath → K.
- Produces: `Future<void> manageUiGroup({required String groupPath, required List<ModData> mods, required Map<String, int> keys, required Future<void> Function(String modPath, int k) manageMod, required String template, required void Function(String message) logError})` — for each keyed mod: write `group_K.ini` (via `renderUiGroupIni`) into `groupPath`, then `await manageMod(modPath, k)`. For a non-disabled mod with no key, call `logError('No free group number for <mod folder name>')`.

**Interfaces:**

- Produces:
  - `final uiGroupProvider = FutureProvider.family<bool, String>` (key: groupPath) → `isUiGroupFolder`.
  - `final uiModOnProvider = FutureProvider.family<bool, String>` (key: modPath) → `readUiOn`.
  - `Future<void> toggleUiMod(WidgetRef ref, ModGroupData group, int viewIndex)` — viewIndex 0 ("None") turns every mod in the group off; otherwise flips that mod: read its `uikey` (if null, do nothing), `writeUiOn`, `simulateKeySelectMod(k, on ? 1 : 0)`, `ref.invalidate(uiModOnProvider(modPath))`.
  - `bool isUiGroup(WidgetRef ref, String groupPath)` — `ref.read(uiGroupProvider(groupPath)).valueOrNull ?? false`.
  - `bool isUiModShown(WidgetRef ref, ModGroupData group, int viewIndex)` — highlight state: for UI groups the mod's `uiModOnProvider` (None card: true when all are off); otherwise `group.previousSelectedModOnGroup == viewIndex`.

Turning on: `setUiGroupFolder(true)`, `writeGroupLoadMode(groupPath, GroupLoadMode.loadAll)`. Turning off: `setUiGroupFolder(false)`, `writeGroupLoadMode(groupPath, GroupLoadMode.inherit)`. Invalidate `uiGroupProvider`. Shows a note that Update Mod Data must be run after changing it.
